# Troubleshooting product integration

| Symptom | Likely cause | Safe check / resolution |
|---|---|---|
| Discovery issuer differs from callback expectations | Product uses an untrusted or incorrect `APP_URL`; URL trailing slash normalization differs | Fetch `/.well-known/openid-configuration` from the configured HTTPS issuer; compare `issuer` exactly with validated ID-token `iss`. Correct deployment config, not a request parameter. |
| `400` / invalid redirect URI | Callback is not an exact Passport registered redirect, contains a mismatch, or client metadata is absent/disabled | Compare byte-for-byte the configured redirect with the value submitted and client record; do not broaden to wildcards. Reconfigure through controlled client registration. |
| `400` invalid scope | `openid` absent, unsupported scope requested, or scope not in this client's allowlist | Request only configured `openid`, `profile`, `email`, `phone`, `product_access` values. `product_access` requires product binding. |
| `403` client not bound to active product | Client metadata lacks product binding, the product is missing/inactive, or `product_access` scope was enabled without `--product` | Verify the product slug is active, then use `oidc:client:configure` with the exact slug and approved scopes. Do not send a `product`/`product_id` authorization parameter; those are prohibited. |
| Authorization request returns to login | Browser has no Central Auth web session, account is inactive/unverified, or session cookie is not sent | Sign in at Central Auth; verify the account is active and verified. For staging/production inspect HTTPS, cookie domain, Secure/SameSite and trusted proxy forwarded proto. Do not disable CSRF or Secure cookies to debug. |
| Consent appears each time | Current flow always displays consent; `require_consent` metadata is not used to skip it | This is current behavior. No consent suppression workflow is documented as supported. |
| Invalid grant at token exchange | Code expired (>5 minutes), already consumed, wrong client/redirect URI/verifier, client configuration changed, or account no longer eligible | Start a fresh authorization request and use the same exact redirect/client and original verifier. Never retry by logging/printing the code or tokens. |
| PKCE fails | Verifier was not retained, wrong verifier used, or challenge method is not S256 | Generate a new transaction with `code_challenge_method=S256`; retain verifier server-side and bind it to state. `plain` is rejected. |
| ID-token signature cannot be verified | Wrong issuer/JWKS, unknown `kid`, cached stale JWKS, wrong algorithm, or key rollover issue | Use trusted discovery/JWKS over HTTPS, select by `kid`, allow only RS256, refresh JWKS safely once for unknown key, and validate issuer/audience/expiry. Do not turn off signature checks. Escalate unresolved key custody/rotation issues to the operator. |
| `nonce` or `state` mismatch | Cross-session callback, replay, stale transaction or wrong transaction store | Reject callback, clear pending login, start fresh. Never ignore mismatches or accept state based only on a user-supplied value. |
| UserInfo returns `401 invalid_token` | Missing, expired, revoked, disabled client, inactive user or token sent incorrectly | Send opaque token as bearer over HTTPS; do not decode it. Reauthenticate after expiry/revocation. Do not log the header. |
| Product-access returns `403 insufficient_scope` | Token was issued without `product_access` | Register scope for a product-bound client and initiate a new login with that scope. Existing token scope cannot be upgraded client-side. |
| Product-access returns binding mismatch | Token's stored product differs from its client metadata, product was disabled, or optional `product` hint conflicts | Remove client-supplied product selection; verify server-side binding/product status. Never rebind to another product to bypass the check. |
| Product-access returns `403 access_denied` | User/membership/permission/feature/subscription/owner/seat condition failed | Check active verified identity; active organization/product; active membership and exact role permission; active/trialing current subscription and active owner; seat limit; enabled `access` and feature entitlements. Keep the denial; do not bypass in the product. |
| Product role allows action but subscription denies | Role permission is only one condition | Subscription and entitlement checks are independent gates; renew/restore through the approved subscription workflow. A role cannot override an expired/suspended subscription. |
| Staff member denied despite owner's plan | Missing active membership, wrong org-scoped role, no required permission, seat count exceeded, owner inactive, or subscription/entitlement not current | Owner assigns an existing active verified account to a role in that organization under an active subscription and available seat. Staff do not automatically buy a separate subscription, but membership and permissions remain required. |
| Product API allows another tenant's record | Product API omitted local ownership check | Treat as product security incident. Enforce tenant filter and resource-to-tenant ownership in database query/policy on every route/job; add cross-tenant denial tests. Central Auth cannot see product records. |
| Logout redirect rejected | Client ID missing, client metadata missing, or post-logout URI not exactly allowlisted | Send POST through the Central Auth browser session with CSRF and exact registered post-logout URI. Do not accept arbitrary return URLs. |
| Logout invalidates more tokens than expected | Current logout revokes all custom OIDC access tokens for that user | This is current behavior. There is no per-client custom token revocation endpoint. Plan product session termination and user reauthentication accordingly. |
| Cross-origin request blocked | CORS defaults to no configured paths/origins | Prefer same-origin/server-side exchange. If a real browser cross-origin need exists, configure exact paths/origins/methods/headers; never use wildcard origins with credentials. |
| Central Auth reports HTTP issuer behind TLS proxy | Trusted proxy configuration is absent/incorrect or `APP_URL` is wrong | Set public HTTPS APP_URL and exact `TRUSTED_PROXIES` IP/CIDRs only for actual proxies. Do not trust all forwarded headers. Verify discovery and redirect URL after deployment. |
| Product-access request returns 401 | Product credential headers are absent/incorrect, credential expired/revoked, OIDC client disabled, product inactive, or user token invalid | Send both server headers plus the user's bearer token over TLS. Reprovision/rotate only through the authorized console command and secret manager. The response intentionally does not reveal which credential check failed. |
| Product-access request returns 403 audience mismatch | Server credential's OIDC client/product differs from the user access-token row's client/product | Use the credential issued for the same exact OIDC client that obtained the user token. Each OIDC client requires a matching credential; same product slug alone does not match the client audience. |
| Product-access request times out | Central Auth unavailable or network/service contract issue | Fail closed. This custom route has no standard introspection SLA or SDK; define bounded timeout/retry and cache policy in the product. |
| Email verification/recovery email is not received | Mailer may be `log`, SMTP/provider config or deliverability may be incomplete | Check non-secret mail configuration state, provider logs and controlled inbox/spam; send a real delivery test. Automated test success is not inbox evidence. SMS/WhatsApp currently fall back to registered email. |

## Incident handling

Never paste authorization codes, client secrets, bearer tokens, ID tokens, cookies, private keys, OTPs or recovery codes into logs or support tickets. Preserve sanitized timestamps, request IDs, client UUID, issuer, `kid`, HTTP status and non-sensitive event references. If compromise is suspected, revoke the affected client or user sessions using authorized Central Auth controls, rotate secrets/keys only through a documented plan, and preserve audit evidence. Do not claim endpoint malware was detected from authentication events.

## Evidence references

Use `tests/Feature/OidcFlowTest.php`, `tests/Feature/OidcClientIntegrationTest.php`, `tests/Feature/ProductAccessTest.php`, and `tests/Feature/AccountSecurityWebTest.php` to identify currently tested behavior. Failures in a separately deployed product still require that product's logs and tests; the Central Auth fixture does not prove the independent application is secure.
