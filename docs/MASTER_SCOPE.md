# VisionWeb Central Authentication — Master Scope v1.1

This is the canonical implementation scope for the VisionWeb Central Authentication project. Version 1.1 is transcribed from the user-approved scope in this conversation. If an older project note conflicts with it, this document takes precedence. New ideas belong in a separate backlog and are not requirements.

## Architecture and operating constraints

- Central authentication owns identity, authentication factors, OAuth/OIDC clients and tokens, verification challenges, trusted devices, security events, audit records, and security alerts.
- Product-specific subscriptions, payments, roles, permissions, and business data remain outside this application.
- Verification messages for email, phone, SMS, and WhatsApp use email delivery until SMS/WhatsApp providers are purchased. Never claim real SMS/WhatsApp delivery.
- Local development only. No live deployment or production infrastructure changes.
- Preserve database data. Never use `migrate:fresh`, reset/drop commands, or destructive data changes.
- Do not expose `.env` values, credentials, keys, access tokens, OTPs, recovery codes, or equivalent sensitive content.
- Actual inbox delivery is verified only after a real mail transport has been configured and tested. Application logs alone do not establish server/OS malware detection.
- Do not invent product policy. Security defaults must be configurable; policy decisions without evidence are recorded precisely.

## Status definitions

- **Verified** — implementation and meaningful behavioral tests exist and pass in the current recorded suite.
- **Implemented, unverified** — code exists, but adequate behavioral evidence is missing.
- **Missing** — no adequate implementation exists.
- **Blocked** — remaining work depends on a specific external resource or decision that is unavailable; repository-side work must still be completed first.
